Phase A · Plan · Functional Scoping & Threat Modeling .agents/skills/threat_model_assessor/SKILL.md

Phase A — Plan: Living STRIDE Threat Model Before Any Code

Features are planned with functional user stories and STRIDE boundary constraints in the same document, so security acceptance criteria exist before the first test is written.

01 · Ingest Context

Read CONTEXT.md First

  • Identifies existing trust boundaries, data flows, and approved security helpers the agent must reuse.
  • history_context_seeder bootstraps CONTEXT.md for legacy repos from commit history.
02 · Decompose & Model

Functional Deliverables × STRIDE

  • Splits the feature into verifiable deliverables.
  • Evaluates Spoofing · Tampering · Repudiation · Info Disclosure · DoS · Elevation for each boundary.
03 · Emit Acceptance Criteria

Write threat_model.md

  • Workspace-root living document with Functional and Security acceptance criteria.
  • Every criterion is phrased as an observable HTTP/API outcome—so Phase B can assert it.
Dogfooded in the Repo

The Framework Models Itself

Living Artifact

threat_model.md (excerpt)

## Feature: Invoice export (sample_app)
### Functional Acceptance
- GET /v1/invoices/{id} as owner      → 200 + JSON
- POST /v1/invoices/{id}/export        → 302 to signed URL

### STRIDE Boundaries (Security Acceptance)
- [I] Cross-tenant read (BOLA)         → 403 / 404
- [T] ?file=../../etc/passwd traversal → 400 (canonical path)
- [S] Missing / expired JWT            → 401
- [T] Open redirect on ?next=          → 400 (allow-list)
- [E] Standard user calls /admin/*     → 403

### Approved Helpers (from CONTEXT.md)
- utils/security.py: safe_path(), safe_redirect(), q()
Exit criterion: threat_model.md updated and every boundary expressed as a status-code assertion.
Phase B · Red · Functional + Security Test-First .agents/skills/security_test_writer/SKILL.md

Phase B — Red: Functional and Boundary Tests That Fail First

One suite asserts both functional outcomes (200 / 302, correct payloads) and defensive boundaries (400 / 401 / 403, validation rejections)—then runs and proves it fails for the right reason.

Pillar 1 · Behavior-Driven Outcomes

Assert on Observable Contracts

  • HTTP status codes and response shapes—never on internals.
  • Functional: 200/302. Boundary: 400/401/403/404.
Pillar 2 · Strict Isolation

Fresh Context Every Test

  • New app context and transaction rollback per test.
  • No order-dependent state; deterministic RED → GREEN.
Pillar 3 · Integration over Mocking

Real Local Instances, Not Fakes

  • Local DB / service instances instead of superficial mocks that hide injection paths.
  • Mocks only where the boundary is external and documented in CONTEXT.md.
Why Co-Verification

Security Is Part of Quality

An out-of-band security patch that breaks an API contract is a production outage. Codifying boundaries alongside happy paths means every fix is regression-checked against business behavior.

RED Assertion (pytest)

tests/test_sample_app.py

def test_owner_can_read_invoice(client, owner_token):
    r = client.get("/v1/invoices/inv_1", headers=auth(owner_token))
    assert r.status_code == 200          # functional

def test_cross_tenant_read_is_denied(client, tenant_b_token):
    r = client.get("/v1/invoices/inv_1", headers=auth(tenant_b_token))
    assert r.status_code in (403, 404)  # [I] BOLA

def test_path_traversal_rejected(client, owner_token):
    r = client.get("/v1/export?file=../../etc/passwd", headers=auth(owner_token))
    assert r.status_code == 400          # [T] canonical path

def test_open_redirect_rejected(client):
    r = client.get("/login?next=https://evil.example")
    assert r.status_code == 400          # [T] allow-list
Exit criterion: pytest tests/ runs and fails for the expected reason. Only then → Phase C.
Phase C · Green · Clean Defensive Implementation .agents/skills/defensive_developer/SKILL.md

Phase C — Green: Minimal Code on Approved Safe Helpers

Author the smallest, cleanest production change that satisfies every failing test—using the project's approved helpers rather than hand-rolled security logic.

Pillar 1 · Strict Input Validation

Schemas & Allow-Lists

  • Type-safe structured schemas (pydantic, extra="forbid") over fragile regex.
  • Allow-list redirect hosts, file roots, enum values.
Pillar 2 · Explicit Authorization

Identity Before Logic

  • Verify caller identity and permission before executing the handler body.
  • Tenant / owner checks live in the data-access signature, not the view.
Pillar 3 · Least Privilege & Safe Sinks

Parameterize Everything

  • Parameterized SQL, canonical path checking, no shell strings.
  • Return the minimum payload the contract requires.
Reuse, Don't Re-Invent

Approved Helpers from CONTEXT.md

sample_app/utils/security.py ships safe_path(), safe_redirect() and parameterized query helpers. Agents are instructed to call these—so one audited implementation guards every route.

GREEN Implementation (Flask)

sample_app/app.py

from utils.security import safe_path, safe_redirect, q

class ExportQuery(BaseModel):
    model_config = ConfigDict(extra="forbid")       # no mass assignment
    file: Annotated[str, StringConstraints(max_length=128)]

@app.get("/v1/invoices/<inv_id>")
@requires_auth                                        # [S] 401 before body runs
def get_invoice(inv_id, principal):
    row = q("SELECT id,total FROM invoices "
            "WHERE id=? AND tenant_id=? AND owner_id=?",
            (inv_id, principal.tenant_id, principal.user_id))  # [I] BOLA
    return (jsonify(row), 200) if row else ("", 404)

@app.get("/v1/export")
@requires_auth
def export(principal):
    p = safe_path(EXPORT_ROOT, ExportQuery(**request.args).file)  # [T] 400
    return safe_redirect(signed_url(p), allow=ALLOWED_HOSTS)      # [T] 302|400
Exit criterion: pytest tests/ is 100% GREEN—functional and boundary tests together.
Phase D · Refactor & Evolve · Quality, Local Scans, Continuous Learning .agents/skills/local_refactor_scanner · skill_evolution_updater

Phase D — Refactor & Evolve: Scan Locally, Learn Permanently

Clean the code, prove 100% regression, run Wiz Code and CodeMender on the changed files, then write the lesson into CONTEXT.md and SKILL.md so the whole agent fleet inherits it.

01 · Code Quality

Refactor & 100% Regression

  • Eliminate duplication, improve modularity.
  • Full suite must stay green—no silent contract changes.
02 · Deterministic Scan Wiz

Changed-File Checks

  • wizcli dir scan --path . → vulnerable / malicious deps, hard-coded secrets, IaC misconfig.
  • Policy pass/fail is identical to CI—no surprises later.
03 · Semantic Scan CodeMender

Find → Verify on Touched Paths

  • cm find ./changed --compact for deep logic flaws linters miss.
  • Guided AI review confirms architectural boundaries from threat_model.md held.
04 · Evolve

CONTEXT.md §4 & SKILL.md

  • Append approved helpers & conventions under Auto-Evolved Conventions.
  • Recurring anti-pattern → propose SKILL.md update (PR for teams, direct edit for solo).
Local Scan Commands (changed files only) 
# Stage 1 — Wiz Code: deterministic SCA · secrets · IaC on the working tree
wizcli dir scan --path . --policy "secure-tdd-code-policy" --policy-hits-only

# Stage 2 — CodeMender: semantic find (+ verify on anything it flags)
cm find $(git diff --name-only origin/main...HEAD | xargs -n1 dirname | sort -u) \
   --model ${CODEMENDER_MODEL:-gemini-3.8-flash} --compact

# Regression gate
pytest tests/ -q
Governance of Skill Evolution

Solo: self-heal · Teams: propose

Individual coding agents should not mutate a shared skill registry. In team settings the evolution phase emits PR proposals or ticket drafts for QA and security leads to review—the lesson still compounds, with a human in the loop.

Engine 2 · Semantic Analysis & Remediation · Gemini Enterprise Agent Platform docs.cloud.google.com/…/agents/codemender ↗

CodeMender — Find, Verify, Fix Deep Vulnerabilities

An AI code security agent that doesn't just flag issues: it builds and exploits each finding to prove it is real, then generates a tested patch. Used in Phase D locally, in Stage 2 of the gate hook, and in CI.

1 · cm find

Find

  • LLM guided by the agent + specialized security tools.
  • Or import findings from external scanners (e.g. Wiz).
2 · cm verify

Verify

  • Builds the code and attempts to exploit the finding.
  • Prioritizes confirmed issues; slashes false positives.
3 · cm fix

Fix

  • Generates a patch idiomatic to the language.
  • Tests it before proposing—fits the TDD loop.
Architecture & Data Posture
  • Agent: hosted multi-agent system (reasoning).
  • Client: local cm CLI + daemon executing in a process-level sandbox (compile, test, exploit).
  • Models: Gemini 3.8 Flash (default) … 3.5 Flash, 3.1 Pro Preview via --model.
  • Never uploads the full repo—only targeted snippets, findings, patches, telemetry.
  • 7-day max retention · explicit delete · ephemeral findings.
  • Zero human access · tenant isolation · VPC-SC support.

Get cm on your PATH

Engine 1 · Deterministic Scanning · Code-to-Cloud Context wiz.io/platform/wiz-code ↗

Wiz Code — Deterministic Policy Gates from IDE to Registry

Fast, repeatable, policy-as-code scanning with one CLI—identical results on the developer's machine, in the gate hook, and in CI—plus Security Graph context linking code to the cloud resources it ships to.

SCA

Dependencies & Lockfiles

  • Vulnerable and malicious packages, licence policy, SBOM.
  • Catches hallucinated / slopsquatted packages before install.
Secrets

Hard-Coded Credentials

  • Keys, tokens, connection strings in source and config.
  • Blocks the classic vibe-coding .env commit.
IaC

Terraform & Kubernetes

  • Public buckets, wildcard IAM, open ingress, missing CMEK.
  • Least-privilege checks before terraform apply.
Containers

Image Scan & Registry Link

  • Base-image CVEs, OS packages, misconfig (root user, no digest pin).
  • docker tag correlates image → running workload.
The Same Four Commands — Locally and in CI 
# Auth: service-account client from Secret Manager (never in the repo)
wizcli auth --id "$WIZ_CLIENT_ID" --secret "$WIZ_CLIENT_SECRET"

# Stage 1 gate — SCA + secrets + IaC in one pass; non-zero exit on policy hit
wizcli dir scan    --path .        --policy "secure-tdd-code-policy"  --policy-hits-only
wizcli iac scan    --path infra/   --policy "secure-tdd-iac-policy"

# After build — image gate, then link to the registry for runtime context
wizcli docker scan --image "$IMAGE@$DIGEST" --policy "secure-tdd-image-policy"
wizcli docker tag  --image "$IMAGE@$DIGEST"
Why Wiz for Stage 1

Deterministic first, semantic second

  • Fast & repeatable — seconds, no LLM variance; ideal as the first gate.
  • Policy-as-code — one policy set shared by hook and pipeline.
  • Hands off to CodeMender — findings import into cm find for verify → fix.
  • Repo note: upstream ships engine_semgrep.sh; Wiz Code is the designated Stage 1 alternative—drop in .agents/lib/engine_wiz.sh.

The Security Gate Hook — Stage 1 Wiz → Stage 2 CodeMender → cm verify

0 · INTERCEPT git push → hook Inspect modified files in the push; detect engines on PATH
1 · DETERMINISTIC Wiz Code scan wizcli dir scan — SCA, secrets, IaC; autofixes where safe
1b · TDD LOOP ≤3 Add test → Fix → Run suite Fixed → import fix + context to Stage 2 · Fails → import finding
2 · SEMANTIC CodeMender cm find Verify imported fixes; ingest remaining findings with full context
2b · TDD LOOP ≤3 Add test → Fix → Run suite Passes → auto-commit & allow · Fails → git checkout .
3 · cm verify Exploit attempt Not exploitable → advisory + allow · Confirmed / crash → HITL (non-TTY: deny)
Hook Registration & Engine Modules (simplified) 
# .agents/hooks.json — universal hook config (Antigravity · Claude Code)
{ "pre-push": [ { "command": ".agents/security_gate_hook.sh" } ] }

# .agents/security_gate_hook.sh — modular entrypoint
source .agents/lib/gate_common.sh        # severity ranking · audit log · notify
source .agents/lib/engine_wiz.sh         # Stage 1 (deterministic)  — wizcli
source .agents/lib/engine_codemender.sh  # Stage 2 (semantic)       — cm

export SECURITY_GATE_ALLOW_ON_ERROR=false  # fail-closed: scanner error ⇒ deny & escalate
export CODEMENDER_MODEL=gemini-3.8-flash   # configurable, never hard-coded
TDD, Not Blind Patching

Every auto-fix is RED → GREEN

  • Reproducing boundary test added first and confirmed failing.
  • Minimal fix, then full-suite regression.
  • Structured commit body: threat boundary, fix, test evidence.
Fail-Open Switch & Audit

SECURITY_GATE_ALLOW_ON_ERROR

  • false → scanner error denies the push and escalates.
  • true → log error, tag commit unverified-scan, proceed.
  • All outcomes → append-only .security-gate/ log; 38 offline mock tests cover PASS · ADVISORY · ERROR · BLOCKED · FIXED.
Layer 3 Backstop · Cloud Build · cloudbuild.yaml Deterministic gates block · Semantic agent opens tested patch PRs

CI Pipeline — Same Engines, Same Policies, Auto-Remediation PRs

1 · TEST pytest tests/ Functional + boundary suite must be 100% green
2 · WIZ DIR SCA · secrets Blocking policy gate
3 · WIZ IAC Terraform / K8s Least-privilege & exposure checks
4 · BUILD Digest-pinned image Multi-stage, non-root, SHA-pinned base
5 · WIZ IMAGE docker scan + tag CVE gate; link to registry / runtime
6 · CODEMENDER find → verify → fix Confirmed issues → tested patch → PR
7 · DEPLOY Cloud Run Only when every gate is green
